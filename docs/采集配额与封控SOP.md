# 采集配额与封控处理 SOP

> 来源：2026-10-20 ~ 10-21 的一次真实事故。当天累计约 88 篇笔记 / 800 条评论后，
> 依次出现 461 验证码 → 接口层限权。复盘结论写在最后。

---

## 1. 症状对照表

先分清是哪一类问题，处理方式完全不同。

| 日志/现象 | 含义 | 处理 |
|---|---|---|
| `CAPTCHA appeared` / HTTP 461 / 471 | 触发验证码，出口被标记 | **立即停止**，等 2–6 小时 |
| `您当前登录的账号没有权限访问` + `Login state: False` | 认证/权限层拒绝 | 先重登；无效则按 §4 判断 |
| `HTTP 429` | 限流 | 等 10+ 分钟 |
| `300011` / `300012` | 账号安全限制 | 停用该账号，等 24 小时以上 |
| 网页正常但接口全拒 | **接口层限权**（本次事故） | 等 24–72 小时 |
| 重登后仍全拒，且冷却无效 | **签名失效**（代码问题） | 更新签名实现，等待无用 |

---

## 2. 配额（硬预算，不是弹性指标）

| 项 | 值 | 依据 |
|---|---|---|
| 单日上限 | **40 篇** | 本次 88 篇撞墙，留一半余量 |
| 单批次 | ≤ 15 篇 | 批次间必须休息 |
| 批次间隔 | 20–30 分钟 | — |
| 评论 | 每篇 ≤ 10 条 | 采集上限，够了 |
| 图片 | 每篇 ≤ 3 张 | 判据 A 只需要 3 张 |
| 时段 | 09:00–23:00 | 凌晨连续采集是机器人特征 |

**88 篇不是安全线，是撞墙线。** 真正的安全线在 40 以下。

---

## 3. 开工协议（探针先行）

任何一次采集前，先跑**一篇**探针：

```bash
.venv/bin/python -m tools.agent_cli start \
  --platform xhs --type search --keywords "<关键词>" --max-notes 1 --media no
```

- 探针成功 → 放量，但不超过当日剩余预算
- 探针失败 → **当天不再尝试**，记入 §6 记录表

这条规则能避免“一上来就跑 40 篇，然后全部失败”的浪费，也能防止在已经被标记的状态下继续加码。

---

## 4. 熔断

| 触发条件 | 动作 |
|---|---|
| 连续 2 次 `DataFetchError` | 停 30 分钟 |
| 出现 461 | 停 2 小时 |
| `Login state: False` 且重登无效 | 停 24 小时 |
| 失败率 > 20%（单批次内） | 立即停，不等报错 |

**失败率上升是最早的预警信号，比报错早半小时以上。** 盯这个指标，不要盯报错。

---

## 5. 恢复判断

冷却结束后，按顺序判断：

1. 网页端是否正常（登录态 / 能否搜索 / 评论区是否加载）
2. 跑一篇探针
3. 探针成功 → 恢复；探针失败但网页正常 → **签名问题，不是封控**
4. 探针失败且网页异常 → 继续冷却

第三步是这次事故最重要的产出：**“网页正常 + 接口全拒”指向代码，不指向风控。**

| 日期 | 动作 | 篇数 | 结果 | 备注 |
|---|---|---|---|---|
| 2026-10-20 | creator + search + 二跳 | ~88 | 15:59 前正常，14:40 起 461 | 首次撞墙 |
| 2026-10-21 15:19 | 探针 3 篇 | 3 | 限权 | 重登无效 |

## 7. 复盘：三次误判

1. **看到 461 就归因“IP 风控 + 额度用完”** —— 错。第二次探针只发 3 篇，仍在第一步就失败。
2. **重登无效后归因“会话过期”** —— 错。两条独立浏览器路径同样失败。
3. **实际是接口层限权** —— 证据：网页正常、失败点在 `query_self`（认证接口）、早于任何业务请求。

**教训：不要用一次报错推断全局。先做最小复现（1 篇探针），再下结论。**

---

## 8. 长期：不依赖实时大批量采集

封控的根本解法不是技术对抗，是**降低对实时采集的依赖**：

- **本地优先**：已有 160 篇笔记，二次分析零请求
- **幂等**：同一 `note_id` 永不重复抓（可省 ~30% 请求）
- **按需展开**：C 端单次查询只展开 40 个节点，而不是全城扫描
- **强缓存**：同一链接第二次查询零请求

**样本设计 > 采集量。** 证明一个簇需要 60 篇，不是 6000 篇。
